# P2Pix Architecture

Blueprint of what we actually ship: the stack, the signing rails, the prover protocol, the read/write layers, distribution, and the build pipeline. The trust roots are the **chain, content hashes, and signatures** — everything else is a deviation, and every deviation is named. [`DESIGN.md`](./DESIGN.md) holds the principles (the technical CROPS pillar and the social pillar, measured by the walkaway test); [`SECURITY.md`](./SECURITY.md) catalogues each trusted party with its escape path, the outbound requests the app makes, the open gaps, and the design-baseline scorecard. This file is _how the pieces are wired and why you can walk away from them_: it does not restate the principles, and it never marks a deviation closed while `SECURITY.md` still lists it open — a fix counts only once it is visible here. Don't just trust the architecture; audit it.

## Concrete blueprint for this dApp

Build-time configuration, injected by CI (the build also bakes in git-derived release metadata and the submodule's deployment addresses, see Build & verification):

- `VITE_APP_ENV` — `production` selects the mainnet network set and the production oracle host; any other value is the development environment: the testnet set and the `demo.*` hosts.
- `VITE_PIX_API_URL` — optional; points the client at another prover, for a local run against `../zkPix`.
- `VITE_WALLETCONNECT_PROJECT_ID` — optional; enables the WalletConnect connector (`src/wallet/wagmi.ts`), which is otherwise left out with a console warning.
- `VITE_MAGIC_PUBLISHABLE_KEY` — optional; enables the email/Google (Magic) connector.
- `VITE_PASSKEY_RP_ID` — optional WebAuthn RP id override (`src/config/aa.ts`) for another owned origin; it must serve `https://<rpId>/.well-known/webauthn`.
- `VITE_PIMLICO_SPONSORSHIP_POLICY_ID` — gates the smart-account rail (`isAaAvailable`) and with it the passkey connector (`src/wallet/wagmi.ts`), per **selected** network: without a bundler on the selected chain, or without this id, the passkey CTAs are hidden and the connector refuses `connect()`.

RPC, bundler and subgraph URLs and the mainnet BRZ addresses are literals in `src/config/networks.ts`; changing one is a code change and a rebuild. This is a disclosed trade-off, not a hidden one: the URLs embed Alchemy and Pimlico API keys — rate-limit credentials that ship in the bundle regardless — so parking them in env vars would hide nothing and buy nothing. The P2Pix contract addresses and the testnet BRZ (MockToken) addresses come from the submodule's `deploys/` records.

Networks: production = Ethereum mainnet and Arbitrum One; development = Sepolia. A network is one `NetworkConfig` entry in `src/config/networks.ts`: the viem chain plus `contracts.p2pix`, `tokens`, `subgraphUrls` and optional `aa` and `swap` blocks; the smart-account rail exists only where `aa` is set, and the CoW swap only where `swap` is set (Arbitrum One). The list is that code registry filtered by the submodule's `deploys/`: a network appears only when its deploy record is present and carries a non-empty `p2pix`, so placeholders and un-deployed networks drop out, and an environment with no wired deployment fails fast at startup rather than shipping an empty network picker. Rootstock Testnet is deliberately not listed: its deploy record predates the current contract and has not been refreshed against it, so the shipped ABIs do not match it.

### 2. Architecture

The QR the buyer scans is the **Brazilian Pix (Bacen EMV) QR** returned by the P2Pix prover; the escrow is released once the contract verifies a **proof of Pix payment** (see Prover protocol).

Signing is client-side on two rails, chosen by the connector the user logged in with (`getAaOwnerKind`, `src/blockchain/aa/aaContext.ts`) and by whether the smart-account rail is available on the selected network (`isAaAvailable`, `src/blockchain/aa/aaContext.ts`). The user always holds the pen: no backend key custody, ever. Every contract write — `approve` and `deposit` in `src/blockchain/sellerMethods.ts`, `lock`, `release` and `withdraw` in `src/blockchain/buyerMethods.ts` — branches on `getActiveAaContext()`: a context means the smart-account rail, null means the EOA rail.

- **EOA rail** — injected wallets and WalletConnect. Each action is a plain transaction via wagmi/viem (`writeContract`); the wallet shows its own prompt, so the human-meaningful action is on screen. The ERC-20 approval is a separate exact-amount transaction — minimal approvals, no blanket allowances.
- **Smart-account rail** — WebAuthn passkey (connector id `passkey` → `AaOwnerKind` `'passkey'`) and email/Google login (connector id `magic` → `AaOwnerKind` `'social'`; `getAaOwnerKind`, `src/blockchain/aa/aaContext.ts`). The signer owns a **Kernel** smart account; every action is a UserOperation, whose hash the signer signs, sent through the **Pimlico** bundler configured for the chain (a replaceable deviation — `SECURITY.md`). When the allowance is short, approval and deposit are batched into one UserOp.
  - **Gas.** Paid by Pimlico's **ERC-20 paymaster in BRZ** when the account holds the minimum fee balance (default in `src/config/aa.ts`, per-chain override in `src/config/networks.ts`) after the batch's own BRZ outflow; otherwise by the **sponsorship policy**. Sponsorship also catches the paid path when the paymaster rejects or fails to quote the token or the quoted cost exceeds the balance; any other quote failure fails the action (`sendAaOperation`, `src/blockchain/aa/operations.ts`).
  - On email/Google login Kernel's owner is the Magic EOA (deviation in `SECURITY.md`) — a key Magic holds, not you (`src/wallet/magic.ts`). On a chain without the smart-account rail (`isAaAvailable` false, e.g. Rootstock Testnet) there is no Kernel: the Magic EOA is the account and transacts on the EOA rail.
  - Passkey RP id (`resolveRpId`, `src/config/aa.ts`, strict): `VITE_PASSKEY_RP_ID` if set, else the longest owned suffix of the page host (`demo.p2pix.co`, `p2pix.co`, subdomains included), else `localhost` in development, else passkeys are off (IPFS gateways, ENS gateways without the override, IP literals, lookalike domains). A passkey is bound to that realm.
  - Passkey login (no server): one discoverable assertion, then a `doiim:passkey*` cache hit, or recovery of the two candidate P-256 public keys from the signature and an on-chain active-address check; if ambiguous, a second assertion restricted to that credential and intersect. The modal has two intents — "Entrar com passkey" (login) and "Criar novo passkey" (create). The session pointer in `localStorage` drives silent reconnect; it is a cache, never `allowCredentials`.
  - **Chain gate.** The passkey connector is built once, for the default network, so it cannot see the app's selection by itself: `isPasskeyAvailable` (`src/wallet/wagmi.ts`) reads it from `useUser`, the modal hides both passkey CTAs with it, and `guardPasskeyConnector` wraps the connector's `connect()` to refuse a chain without the smart-account rail. Hiding the CTA alone is not enough — the connector stays registered, and a stored session keeps `isAuthorized()` true, so a programmatic `connect()`, or wagmi's reconnect on mount, would otherwise bring up a Kernel account on a chain the app can display but never transact with.
  - **Escape path:** Enviar in the account panel beside the offer card (`SendView`, `usePasskeyAccount.send`), on either smart-account login, lets the user send each of the smart account's tokens, one at a time, to any address — a sovereign exit from the smart account. Gas is paid through the ERC-20 paymaster, so a BRZ send needs a BRZ balance.

On both rails the new lock's id is read from the `LockAdded` event in the transaction's own logs, since `lockID = ++lockCounter` is global (`getLockIdFromLogs`, `src/blockchain/buyerMethods.ts`) — the log is the receipt, not a server's word for it.

Both rails act on the network selected in the UI: wallet clients are requested from wagmi for that chain, viem checks the wallet's chain before every EOA write, and the ERC-20 paymaster path re-checks the quoted chain and sender before submitting (`src/blockchain/provider.ts`, `src/blockchain/aa/paymasters/erc20.ts`); a banner (`ToasterComponent.vue`) flags a wallet on another chain and offers to switch it.

The address shown and used for reads is the smart-account address on the smart-account rail and the connector address on the EOA rail (`getEffectiveWalletAddress`).

**Post-release swap (optional, Arbitrum One).** P2Pix escrows and releases only BRZ; another token is a CoW order placed by the buyer's own account after release.

- **Quote and lock.** When the buyer picks a swap token, the search screen asks CoW for a buy quote of the typed amount and locks `quote × 1.02 + fee reserve` BRZ — which is also the Pix amount in R$ (`quoteLock`, `src/blockchain/swap.ts`). The 2% absorbs price drift during the Pix; the reserve covers the paymaster's BRZ charge. Price impact against a quote for 1% of the amount is shown above 1% and never blocks. The choice is kept in `sessionStorage` per lockID, so a reload between lock and release keeps it.
- **Order.** `kind: buy` for the typed amount, receiver = the buyer, sell limit = released BRZ − fee reserve, valid 30 minutes. It is built locally (`buildOrder`, `src/blockchain/cowOrder.ts`); from the API it takes only the price, and the uid the API returns must equal the locally computed one.
- **Smart-account rail.** The order is posted as `presign` first; `release`, `approve(vaultRelayer, sellLimit)` and `setPreSignature(uid, true)` then run as one UserOp.
- **EOA rail.** When the wallet reports atomic batching (EIP-5792 `wallet_getCapabilities` → `atomic: supported | ready`; MetaMask and Coinbase via EIP-7702), the order is posted as `presign` and `release`, `approve` and `setPreSignature` go out as one `wallet_sendCalls` prompt — atomic, and still sent by the buyer's own address, so `release` credits the buyer. Otherwise `release`, then an exact `approve` when the allowance is short, then the EIP-712 order signature and post; the release screen says up front that these prompts all belong to the trade (`separatePrompts`, `src/utils/walletPrompts.ts`).
- **Fallback.** If the price no longer fits the sell limit or the order book fails, release still runs and the buyer gets BRZ. The status card (`SwapOrderStatus.vue`) polls the order and offers a re-quote (sell the BRZ now in the account at the current price, 1% slippage) or "Ficar com BRZ" (smart account: `setPreSignature(uid, false)` + `approve(…, 0)`; EOA: a signed off-chain cancellation).

**Sell-side swap (optional, Arbitrum One).** A seller can pay with a swap token instead of holding BRZ. The sell form quotes CoW for the BRZ of the offer (`quoteBrzCost`) and shows the cost, the price impact above 1% or "no route". On submit the seller's own account places a `kind: buy` order for exactly the offer's BRZ, spending up to the quote plus 2% (`buyBrz`, `src/blockchain/swap.ts`), on the same rails as the buy side (smart account: approve + `setPreSignature` in one UserOp; EOA: one EIP-5792 prompt, or approve + EIP-712 signature). The deposit cannot ride the order as a CoW hook — `deposit` credits `msg.sender`, which would be the hooks trampoline — so `SellerView.vue` waits for the order to fill (`SwapOrderStatus.vue`, shared with the buy side) and then runs the usual BRZ approve + deposit. An unfilled order expires with the token still in the seller's wallet; the card offers a re-quote or a cancel.

Order book calls (`swap.apiUrl` in `src/config/networks.ts`, client in `src/utils/cowApi.ts`; every response is shape-checked):

| Call | When | Request → response |
| --- | --- | --- |
| `POST /api/v1/quote` | Search screen input; again just before release; on re-quote | tokens, buyer address, kind and amount → `sellAmount`, `buyAmount`, `feeAmount` |
| `POST /api/v1/orders` | Before the release UserOp (presign) or after the EOA signature | the locally built order + signature → order uid |
| `GET /api/v1/orders/<uid>` | Polled every 10 s while the order is live | → `status`, `executedBuyAmount` |
| `DELETE /api/v1/orders` | "Ficar com BRZ" on the EOA rail | `{ orderUids, signature }` signed over `OrderCancellations` |

### 3. Prover protocol (proof of Pix payment)

The client talks to the P2Pix prover at `https://api.p2pix.co` in production and `https://demo.api.p2pix.co` in development (`src/utils/bbPay.ts`). The prover creates and reads solicitations through Banco do Brasil's **BB Pay** API; the development prover runs against BB Pay's sandbox, where confirmations are simulated. Endpoints:

| Call | When | Request → response |
| --- | --- | --- |
| `POST /register` | Seller creates an offer, before `deposit` | bank account details → `numeroParticipante`; the on-chain `pixTarget` is `<chainId>-<numeroParticipante>` |
| `POST /request` | After the buyer's `lock` is mined | `{ amount, pixTarget, lockId, chainId }`, with the bare `numeroParticipante` read back from the chain (`getPixTarget`); the prover writes `<chainId>-<lockId>` into the charge's reconciliation code → `numeroSolicitacao` plus the EMV "copia e cola" string rendered as the QR |
| `GET /release/<numeroSolicitacao>` | Polled while the QR is shown | `402` until the bank confirms the buyer's Pix, `202` while the proof is produced, then `{ numeroSolicitacao, proof }`: the proof of Pix payment |

The buyer pays the Pix into P2Pix's BB Pay account and BB settles it to the seller's registered account in the same flow. Fiat therefore transits P2Pix's account for the settlement window — a custody deviation, disclosed in `SECURITY.md`. The buyer view (`QrCodeComponent.vue`) polls `/release` until a reply carries the proof, then submits it on-chain.

Release is `release(lockID, proof)` (`releaseLock`, `src/blockchain/buyerMethods.ts`), verified on-chain (`p2pix.sol` `release` → `core/BaseUtils.sol` `_proofCheck`). The proof is the Primus attestation of the bank's own answer (see zkPix):

- the contract rebuilds the attested request from its bank settings (`bank`: URL prefix and suffix, the suffix carrying the convênio query) and the proof's solicitation number, recomputes the digest the attestor signed, recovers the signer and requires it to be in `validAttestors`, and the proof's recipient to be the configured `prover`;
- it then reads the revealed fields and requires the charge to be settled in full, its amount to equal the lock's, its recipient to be the lock's `pixTarget` rebuilt as `<chainId>-<payee>`, its reconciliation code to be `<chainId>-<lockID>`, and the attestation to be younger than `proofMaxAgeMs`; each Pix `txId` is accepted once;
- `setValidAttestors`, `setBankConfig`, `setProver` and `setProofMaxAgeMs` are owner-only, and the attestor set is the trust anchor — **readable on-chain** (`validAttestors`), so anyone can audit exactly who is trusted;
- `release` is public and always pays the lock's buyer, whoever calls it.

The proof binds the lock itself, through the reconciliation code the prover wrote when it created the charge, as well as the seller's participant number and the amount. Once a lock expires, `release` reverts and the escrow returns to the seller's deposit when someone calls `unlockExpired` (the prover-walkaway open gap in `SECURITY.md` — a fund path that must not need us).

### 4. Read-only layer

Reads are split by concern so that no single party is silently authoritative:

- **Subgraph for discovery.** Deposit lists and liquidity, wallet history and the Explore view's activity and analytics come from The Graph (`src/blockchain/events.ts`, `src/blockchain/wallet.ts`, `src/composables/useGraphQL.ts`). The subgraph is an _index_; the chain is authoritative.
- **RPC for authority.** Money amounts are read from the chain with viem `readContract` / `multicall` (`getBalance`, `mapLocks`, `getLocksStatus`, `getPixTarget`, `userRecord`, ERC-20 `allowance` / `balanceOf`); which deposits and locks to read is discovered through the subgraph. The buyer's spend limit comes from a separate Reputation contract, whose address the P2Pix contract reports (`reputation`, `limiter`; `src/blockchain/reputation.ts`).
- **Seller allowlist.** A seller may set a Merkle root of buyer addresses for their account (`setRoot`, read back with `sellerAllowList`); a buyer on that list passes a proof to `lock` and skips the reputation limit, while everyone else keeps the normal limit — the list relaxes, never blocks. A lone buyer is paired with a zero leaf so the proof is never empty. The contract stores only the root. The addresses never reach a server: the seller's list (with private nicknames) and the lists buyers import live in `localStorage` (`src/utils/allowlistStorage.ts`), moved between people as a `.json` file the seller downloads and sends, and a list is used only when its recomputed root equals the seller's on-chain root (`src/blockchain/allowlist.ts`, `src/utils/allowlist.ts`; UI in `/allowlist`). Every buyer who gets the file sees every address and nickname on it.
- **Whose RPC.** Reads use the app-supplied wagmi transports: `createConfig` in `src/wallet/wagmi.ts` builds each chain's transport as `http(<first RPC URL>)` from `src/config/networks.ts` with no other read fallback. The Alchemy URLs there also serve the passkey connector's on-chain reads and Magic, which are handed the default network's URL. They are deviations — metadata-visible read providers — and the configurable-infra switch is an open gap in `SECURITY.md`. The zero option we owe is pointing the app at your own RPC and subgraph.
- **Direct contract escape path.** Every P2Pix contract action the UI performs — `deposit`, `lock`, `release`, `withdraw` — is a public function callable with any EIP-1193 wallet against the deployed address, without this frontend. The app is a convenience, not a permission slip.

### 5. Distribution layer

One workflow, `.gitea/workflows/ci.yml` (`CI & Deploy`), builds every branch and tag push, PRs and manual dispatches. Build mode follows the audience: PR previews, `main` and tags build production (`VITE_APP_ENV=production`, mainnet config); other branch pushes build development (testnet config). It installs, lints, checks formatting, generates the ABIs, runs the unit tests, builds, then deploys from hosted CI runners — team-run infrastructure, a deviation (`SECURITY.md`, walkaway requirements):

- **Self-hosted server.** `dist/` is rsynced over SSH into a directory named after the ref. Development builds are served at `*.demo.p2pix.co`.
- **IPFS.** `dist/` is merkleized in CI, SHA-256 and CID profile pinned in the workflow; the resulting CAR is uploaded to a remote pinning service, which pins the root CID.
- **IPNS.** An IPNS name, anchored by the `_dnslink.p2pix.co` TXT record is resolvable as `ipns://p2pix.co`.

### 6. Build & verification

- **Release metadata is compiled in.** `vite.config.ts` reads the git tags, notes and HEAD at build time and inlines them as `import.meta.env.APP_VERSION` / `APP_RELEASES`. The version is `package.json` `version`, plus `+<short sha>` when HEAD is off the tag of that name; without git, for example from a source tarball, the bare version is emitted.
- **CID per tag is a manual step.** After a release the maintainer records its CID with `git notes --ref=ipfs add` (README "Versioning"); CI fetches the notes and the maintainer writes them. Notes rather than tag messages, so history stays clean and a wrong CID is fixable with `add -f`.
- **Versions view.** `src/views/VersionsView.vue` lists the tags compiled into the bundle and links the ones carrying an IPFS note to `ipfs://<CID>`; the list is self-reported.

### 7. zkPix

`zkPix` is the release path described above: the contract verifies a **proof of Pix payment**, produced with **zkTLS** from the bank's own confirmation, in place of a signature from a party we operate. The prover lives in a separate repository (`zkPix`), public at `git.p2pix.co/doiim/zkPix` under AGPL, and the submodule pin carries the proof-verifying contracts — a clean checkout generates matching ABIs and this frontend type-checks against them.

- **Prover flow.** On `GET /release/<n>` the prover reads the charge from BB Pay and, once the bank reports it paid, opens a Primus network task (Base Sepolia in development) and has the selected **Primus attestor** replay one request to the bank over zkTLS in proxy mode with the prover's mTLS client certificate and a read-only OAuth token: `GET /solicitacoes/<n>`.
- **Attestor signature.** The attestor signs — a raw keccak over the packed attestation — the request URL, the JSON paths it was asked to reveal and the revealed values: amount, settled sum, payee, Pix `txId` and reconciliation code.
- **Proof handoff.** The prover checks the signature itself, caches the proof per charge and answers it verbatim; the client passes it to `release`.
- **Soundness.** The contract's bank settings and the fixed JSON paths in `Constants.sol` are what the attestor is asked to attest, so a proof of any other request or field cannot verify. What stays trusted is in `SECURITY.md`.
